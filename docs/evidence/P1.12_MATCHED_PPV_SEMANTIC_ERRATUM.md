# Semantic erratum — `median_threshold` in `matched_ppv.py`

**Status: ERRATUM. The frozen artefact is left unchanged, deliberately.**
Dated 2026-08-22. Documentation/schema defect only — **not** a P1.11 runtime correction.
Issued under [P1.11_PROVENANCE_AND_FAILCLOSED_CORRECTION.yaml](../plans/P1.11_PROVENANCE_AND_FAILCLOSED_CORRECTION.yaml), Phase 3.

---

## The defect

[`scripts/p1_12/matched_ppv.py:190`](../../scripts/p1_12/matched_ppv.py) stores the fixed frozen
v1.1 operating point under a key whose name means something else:

```python
blk["A_v11_frozen"] = {"nested": {..., "median_threshold": 0.9524}, ...}
```

**0.9524 is not a median of anything.** It is a single fixed constant — the v1.1 standard deployment
threshold adopted post-P1.10 by
[P1.10C](../plans/P1.10C_V1.1_DEPLOYMENT_OPERATING_POINT_AMENDMENT.yaml).

The key name is correct everywhere else in the same file. At `matched_ppv.py:142` the same slot is
genuinely computed as a median:

```python
"median_threshold": float(np.nanmedian(thr))
```

That line is the out-of-fold candidate-model path, where a median over per-fold thresholds is
exactly what the value is.

The actual median of the five development fold thresholds `[0.9732, 0.9605, 0.9378, 0.9718, 0.9524]`
is **0.9605**, not 0.9524 — so a reader who trusts the key name at line 190 would conclude the
frozen v1.1 comparator ran at the median, and would have the wrong value and the wrong provenance
story.

## Impact assessment

| question | finding |
|---|---|
| Does any frozen evidence artefact consume this key? | **No.** `median_threshold` appears nowhere under `docs/`. |
| Where does the output go? | `scripts/p1_12/matched_ppv_results.json` — a development working file, not committed evidence. |
| Is any published number wrong because of it? | **No.** The value stored is 0.9524, which is correct; only the key *name* misdescribes it. |
| Is the script hash-pinned? | **Yes** — `docs/evidence/P1.12_PRE_JOIN_HASH_RECEIPT.md:51` pins `matched_ppv.py` at `a5218521dfad9fc7c7845f6a1096b33da34e1b10daab0ec503a73b5a7fbbeaa5`. |
| Is it on the P1.11 runtime path? | **No.** It is a development-phase frontier tool. It is not imported or invoked by the evaluator, the router, or any P1.11 execution step. |

## Decision — erratum, not a rename

Of the two options the correction authorises, the frozen artefact is **left unchanged**.

Renaming the key to `v1_1_standard_threshold` would:

- change the file's SHA-256 and therefore **invalidate a pinned hash** in the pre-join receipt, for
  a value that is already numerically correct;
- require regenerating `matched_ppv_results.json`, which risks **recomputing the frontier** — the
  one thing Phase 3 explicitly forbids;
- gain nothing operationally, since no consumer reads the key.

Changing a pinned development artefact to fix a comment-grade naming defect trades real provenance
for cosmetic tidiness. The erratum is the proportionate remedy.

## The correct reading, for anyone using this file

> In `matched_ppv.py`, the key `median_threshold` inside `A_v11_frozen.nested` (line 190) holds the
> **fixed v1.1 standard deployment threshold 0.9524**, not a median. It is not derived from the data
> in that run. The identically-named key at line 142 *is* a genuine median, computed over per-fold
> thresholds for the out-of-fold candidate models. The median of the five development fold
> thresholds is **0.9605**.

## Scope

Nothing was recomputed. No threshold, frontier, matched-PPV figure, model, coefficient or endpoint
was touched. `matched_ppv.py` and `matched_ppv_results.json` are byte-unchanged.
