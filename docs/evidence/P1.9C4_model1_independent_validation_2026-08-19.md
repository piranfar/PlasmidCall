## 5. Version/database compatibility and the limitations that actually matter

- **FUNCTIONALLY_COMPATIBLE** (same tool and role, not historically identical): HyAsP (2022-05-12 commit + figshare gene DB; putative plasmids only),
  PLASMe 1.1 + Zenodo DB (contig ids given a reversible `c` prefix because v1.1 discards purely numeric ids), PlaScope (Centrifuge **1.0.4** + PlaScope

  Unicycler headers), Plasmer 0.1 (pinned Docker digest + Zenodo DB v1.0), PlasmidEC 1.3 (GFA mode as recommended for gplas2; component environments
  pre-pinned to the versions its own script installs, including centrifuge 1.0.3; `-t` omitted because of a getopts defect in v1.3, leaving its default
  8 threads), PlasmidFinder 2.0.1 (database tag "2.2.0" resolves to a commit dated 2025-09-10 — the paper's snapshot is not recoverable), gplas2 1.1.0,

- Product A assemblies are Unicycler **0.5.1**; the development set used 0.5.0. Header-normalised copies (`>id`) were supplied to tools whose scripts
  break on spaces in FASTA headers — identifiers and sequences are unchanged, and the identifier audit is exact for all 8 samples.
- **The ARG-bearing definition differs from the development set**: AMRFinderPlus 4.2.7 core AMR (`Element type = AMR` and `Element subtype = AMR`)

  0.71 in the development data). Model 1's ensemble logic absorbed that noise — 1 false positive for M0 and none for M2 — which is itself a supported
  finding about the robustness of the frozen rules to a degraded member.
- The M2-only feature "Number of SR contigs" is the count of contigs ≥ 1 kb per sample.
- All compatibility work was execution- and format-level. The 12-column schema, the value vocabulary, the M0 rule and the M2 specification (candidate

## 7. Conclusion

On an independent 8-isolate *E. coli* cohort with clean-room truth, the frozen Model 1 specifications retain their high-precision character —
M0 PPV 1.000 (16 calls) and M2 PPV 1.000 (14 calls) with zero false positives on ARG-bearing contigs, and 0.983 / 1.000 across all 739 resolved
contigs — but do not reach the recall target (0.485 / 0.424 primary; 0.400 / 0.372 secondary). The programme conclusion recorded in
`MODEL_VALIDATION_STATUS.md` §1.6 — high PPV, insufficient recall, classification target NOT YET MET — is **externally confirmed** under
deployment-era tool and database versions.

## 8. Frozen scientific interpretation and status determinations

**Authoritative conclusion (frozen 2026-08-19):**

> On an independent same-isolate hybrid-reference benchmark, Model 1 retained its high-precision behavior but did not achieve the prespecified recall
> target. Both M0 and frozen M2 produced no false-positive plasmid calls in the primary ARG-bearing set, but effective plasmid recall was 48.5% for M0
> and 42.4% for M2. M0 therefore validated as a selective high-confidence rule-in detector with abstention, whereas M2 did not demonstrate superiority
> and neither model validated as a comprehensive high-recall classifier.

Several *individual* tools achieved substantially higher plasmid recall than either ensemble rule while remaining high-precision — on the secondary set
MOB-recon 0.979, HyAsP/Plasmer/PlasmidEC ≈ 0.89–0.95 recall — yet M0 and M2 deliberately hold a stricter high-precision operating point (M0 abstains,
M2 uses a 0.9776 threshold). This is a genuine, non-hidden result: the ensemble trades recall for precision by design, and on this cohort that trade
produced zero (M2) or one (M0, secondary) false positive. Model 1 is a high-confidence plasmid **rule-in** with limited recall; it is neither useless
nor comprehensively validated.

## 12. ERRATUM and re-scoring at the development-derived operating point (2026-08-19, P1.10-A/B/D)

An independent read-only audit of this stage established a material defect in **the operating point used
here, not in the pipeline, the predictions or the truth**. This section is an erratum to §1, §2 and §7.

**The defect.** The frozen threshold rule ("smallest threshold with inner-OOF PPV ≥ 0.95 and ≥ 10 positive
calls") was applied in P1.9C4 by fitting **once on the full 1,460-row development set**, giving `0.9776`.
Development applied the *same rule* **per outer fold**, giving `0.9732, 0.9605, 0.9378, 0.9718, 0.9524`
(`out_p15_folds_M2.csv`) — `0.9776` is stricter than **every** development fold. The verdict "recall
target NOT MET" therefore was not robust to the threshold realisation.

**Development reproduction (the check that was missing).** The frozen procedure was re-executed on the
development data and reproduces **bit-exactly**: M2 TP 189 / FP 13 / TN 1167 / FN 91, PPV 0.9356435643564357,
recall 0.675; M0 104/5/1117/0/234; fold thresholds and their median `0.9605` confirmed.
Receipt: `docs/evidence/P1.10B_dev_m2_reproduction_receipt.json` (sha256 `a1476fd8…4624f`).
