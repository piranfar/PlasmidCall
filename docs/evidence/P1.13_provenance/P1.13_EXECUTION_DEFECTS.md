# P1.13 execution-path defects found and fixed

**Dated** 2026-08-22 | Implementation defects only. No change to cohort membership, run accessions,
target depth, seed, sampling algorithm, assembler, tool panel, models or thresholds.
Cohort sha256 prefix `2e47d15b30a42181` unchanged throughout.

All four defects share one property: the artefact looked correct to the obvious check and was
wrong at the point of use. None would have been caught by counting, sizing, or listing.

## 1. Resume-onto-corrupt during acquisition

`curl -C -` resumed onto files left partial by an interrupted run, appending from the wrong logical
offset. One file came back **exactly the declared size with the wrong content** and would have
passed any size or record-count check. md5 was checked only after the retry loop, so a corrupt
file could never be recovered: each retry resumed onto the same corruption.

Fixed: an md5-failing file is corrupt, not partial. It is deleted and refetched from byte zero,
and md5 is checked inside the retry loop. Result: 150/150 verified, 0 failed.

## 2. Unenforced minimum coverage

The frozen design declares `minimum_usable_coverage: 30x`. Nothing in the execution path enforced
it. Selection used ENA's **declared** coverage; the downsample receipts are the first place
coverage is recomputed from actual sequenced bases, and the two can disagree.

Fixed: the floor is enforced where coverage is recomputed, failing closed.
Audit over all 150 receipts: **0 isolates below 30x**, lowest raw depth 34.61x. The floor did not
exclude anyone; it is now guaranteed rather than assumed.

## 3. Symlinked reads that dangle inside the container

For the 56 isolates already below 100x, no downsampling is required and the verified raw reads were
linked into `down/<isolate>` with an **absolute symlink** into `raw/`. The assembly container mounts
only `down/<isolate>`, so inside the container the link pointed at a path that does not exist.
`ls` on the host showed the file; the container reported `could not find /reads/R1.fastq.gz`.

This would have destroyed **56 of 150 isolates, 37% of the cohort**, with an error that reads like
missing data rather than a mount defect.

Fixed: hard links. `raw/` and `down/` share a filesystem, so the container sees a real file at no
storage cost. 112 links converted in place, 0 unresolved; `/data` usage unchanged.

## 4. Output directory not writable by the container user

The assembly container runs as `mambauser` (uid 57439). The scratch directory was created with
mode 777; the **output** directory was created with `mkdir -p` and no mode change, owned by
`ubuntu` (uid 1000).

Consequence: every assembly ran to completion, SPAdes succeeded, and the final copy failed with
`cp: cannot create regular file '/out/shortread.fasta': Permission denied`. The work was then
discarded when the scratch directory was removed. 15 isolates burned full assembly compute and
produced nothing.

Fixed: all 150 output directories pre-created writable. This repaired the in-flight assemblies as
well as queued ones without editing a script that was mid-execution. First assembly then succeeded:
235 contigs, 5,905,222 bases, longest contig 309,627 bp.

The 15 previously failed isolates are retried automatically, because the phase-3 loop skips only on
a `.done` marker.

## Note on why phase 2 was re-run

Phase 2 was serial on a 64-core machine. It was parallelised to 12 concurrent, which required
per-isolate scratch directories. Determinism was **verified, not assumed**: an already-completed
isolate re-run under the new code returned a bit-identical result, including the id-stream digest
over 1,704,891 retained pairs. Each isolate is a pure function of its own reads, its own recomputed
fraction and the frozen seed, so execution order cannot affect any output.
