## Why: the supplementary table could not be retrieved

The article's data statement is explicit that the accessions live in Supplementary Table 1:

> "The data underlying this article are available in the Sequence Read Archive … and the
> BioSample database … (and can be accessed with the accession numbers in Supplementary
> Table 1)"

Every retrieval route was tried and each failed:

| Route | URL | Result |
|---|---|---|
| PMC supplementary file | `pmc.ncbi.nlm.nih.gov/articles/instance/12602193/bin/circling_in_on_plasmids_-_supplementary_tables_bbaf589.xlsx` | HTTP 200 but **1,816 bytes of HTML**, not the 3 MB XLSX — a JavaScript proof-of-work interstitial (`POW_CHALLENGE`, `POW_DIFFICULTY 4`, cookie `cloudpmc-viewer-pow`) |
| Publisher article page | `academic.oup.com/bib/article/26/6/bbaf589/8320154` | **HTTP 403** |
| bioRxiv supplementary media | `.../2025.07.28.667252/DC1/embed/media-1.xlsx` | **HTTP 404** |
| bioRxiv supplementary page | `.../2025.07.28.667252v2.supplementary-material` | **HTTP 520** |
| NCBI BioProject text search | E-utilities `esearch` for the study | **0 hits** for the tried phrasing |

**I did not attempt to solve the proof-of-work challenge.** Defeating bot-detection
programmatically is out of bounds, and the correct response is to report the block rather
than to work around it. The HTML interstitial that was returned instead of the file is
retained as the retrieval receipt: `suppl_tables.xlsx` (misnamed by the server's
content-disposition), 1,816 bytes, MD5 `4f7d43c5eb0f5240837ea3b1d6285a14`, SHA-256
`85567250e7221198f92ecfa49677d96cfce57d88a467cb4307deb8fed7cbffd8`, accessed 2026-08-17 UTC.

## Consequence

The independence of the development benchmark from any archive-indexed corpus — including
the plasgraph2 public-source cohort — **remains untestable at identifier level**. This was
the single largest gap identified in P1.9A and it is unchanged.

1. **The owner downloads the file.** `Circling_in_on_plasmids_-_Supplementary_Tables_bbaf589.xlsx`,
