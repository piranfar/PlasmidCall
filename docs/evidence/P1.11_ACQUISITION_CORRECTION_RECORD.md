# P1.11 acquisition — correction record

**Status: `CONFIRMED`.** Acquisition completed with every input verified against a frozen record
before any assembly began. This document records five defects encountered during acquisition, four
of which were mine, and the evidence that none of them let an unverified input reach assembly.

Dated 2026-08-21. Execution-only: no scientific parameter, cohort member, threshold, endpoint or
truth rule was changed at any point.

---

## 1. TSV parsing defect — one file deleted

**What happened.** `p111_acquire.sh` read the manifest with `IFS=$'\t' read -r …`. Bash collapses
*runs* of IFS whitespace, and **tab is whitespace**, so rows with empty fields had their remaining
fields shifted left. The four SRA-only rows carry empty `url` and `md5`, so:

| row type | parsed as |
|---|---|
| SRA row | `route=[]` `defer=[]` `md5=[GENOMIC]` `url=[MiSeq i100]` — **shifted** |
| ENA row | `route=[ENA]` `defer=[False]` `md5 len=32` — correct |

The `route == "SRA_ONLY"` guard therefore never fired. The script treated an SRA-generated FASTQ as
a corrupt ENA download and **deleted `SAMN53177110/SRR36382631_1.fastq.gz`**.

**Blast radius, measured.** Only the 8 SRA rows mis-parsed. All ENA rows have every field
populated, so no collapse occurs. The other 7 SRA files verified byte-exact against their recorded
SHA-256 at the time of the incident.

**Fix.** The manifest is split with `awk` (which does not collapse empty fields), and each row is
validated before use — `route == ENA`, non-empty URL, md5 exactly 32 chars — aborting loudly rather
than acting on a mis-parsed row.

The regenerated `.gz` has a different SHA-256 from the original because **gzip embeds an mtime in

## 3. curl resume/retry interaction

`curl -C -` resolves its resume offset **once at startup**. Each internal `--retry` therefore
restarts from that original offset and truncates whatever the failed attempt gained. Observed
progress oscillated 357 MB → 485 MB → 357 MB with no net advance.

**Fix.** One curl attempt per outer-loop iteration, so each pass re-reads the true file size.

## 4. Oversized and gzip-corrupt partials — root cause was concurrent writers

A resumed transfer produced a file of **1,381,273,600 bytes against an expected 1,220,022,287**,
and a later attempt produced a 550 MB file failing `gzip -t` with
`invalid compressed data--format violated`.

**This was initially misattributed to ENA.** The true cause was **two of my own background jobs
writing the same path concurrently** — one looping with `-C -` resume, another doing a single-pass
download, plus a third process watching the file size. Process `686427` had been looping for
10 minutes 51 seconds while new jobs were started on top of it. They truncated and appended over
each other.

The diagnostic that should have been decisive immediately: **a file growing larger than its known
size cannot be a network failure mode.** It can only be concurrent writers.

**Fix.** One writer per file, ever. Drain before restart. Oversized partials are discarded rather
than resumed.

Once all competing writers were killed, the file downloaded and verified on the **first clean
attempt**:

| check | result |
|---|---|
| size | 1,220,022,287 — exact |
| md5 | `06bc63e5477a463e6c860f4bbd4c339b` — matches frozen manifest |
| `gzip -t` | valid |
| reads in R2 | 15,754,694 |

The TLS drops (`curl 56: SSL_read unexpected eof`) were real but always recoverable; they were never
the reason a file ended up corrupt.

## 5. Chunked acquisition adopted for large files

A single uninterrupted 1.22 GB TLS transfer is unnecessarily fragile. `scripts/p1_12/fetch_chunked.py`
downloads large objects as independent fixed-size ranges (64 MiB default) and **never appends a
retry onto an unverified partial**:

- explicit inclusive byte range per chunk
- **HTTP 206 required, never 200** — a 200 means the server ignored the range
- exact `Content-Range` echo required
- exact chunk length required
- each chunk in its own uniquely numbered temporary file
- failed chunks retried independently from a clean slate
- verified chunks concatenated once in strict numeric order
- candidate accepted only after size + md5 + gzip all pass, then renamed atomically

**Fixture suite: 9/9 pass**, including rejection of range-ignored 200 responses, wrong
`Content-Range`, short chunks, md5 mismatch and wrong expected size, and confirmation that no output
file is written when a candidate is rejected.

## 6. Acquisition route unchanged

`SAMN53536567` remained on **ENA** throughout. It was never switched to SRA to bypass a transport

The four SRA-only isolates remained on **SRA** (`prefetch` → `fasterq-dump`), and an ENA-mirror

- Every ENA file was verified against the **frozen manifest md5**, not against a value computed at

- A corrupt file could never acquire the final filename: candidates are only renamed after passing

## Lesson recorded

Four of the five defects were mine, and three share one shape: **I disturbed state that something
else was actively using** — concurrent writers on one file, a script edited while a loop was
interpreting it, and monitors whose own command strings polluted their own measurements. The
remedies are the same in each case: single writer, drain before change, and never let a measurement
pattern match the measurer.
